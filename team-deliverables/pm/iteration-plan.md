## 1. 现状回顾与能力基准诊断

### 1.1 现有系统能力基准 (As-Is State)

LibreTV（cl.tv）是一款现代化流媒体视听与 IPTV 聚合平台，基于 **元数据中心化 + JIT（即时）多源切片流匹配** 双层解耦架构开发。在先前的 v1.1 迭代中，团队针对首页图片加载延迟与播放源并发测速进行了专项攻坚并成功合并入 Master 分支。

当前系统的功能完备度基准如下表所示：

| 模块 / 路由 | 当前已具备能力 | v1.1 性能优化成果 | 现有局限与不足 |
| :--- | :--- | :--- | :--- |
| **首页** (`/`) | Hero 巨幕 4K 趋势轮播、热播飙升榜、官方影视资料库精准搜索、底层采集源深度流式扫描、Spotlight 搜索 (⌘K)。 | `SmartImage` 视口延迟（200px）+ 骨架屏 + eager/priority 首屏加速，LCP ≤ 2s；TMDB 尺寸自适应重写，网络体积降幅 ≥ 40%。 | 缺乏针对“追剧单有新集更新”的主动聚合展示，用户无法一眼获知所追剧集的更新动态；首页搜索历史与热门搜索词缺乏前置下拉联想。 |
| **播放页** (`/watch`) | ArtPlayer + hls.js 深度调优播放器、自动连播、0.5x~3.0x 倍速、移动端长按 3 倍速、快捷键、跨屏扫码接力 (QR Handoff)、离线 MP4 下载、断点续播 (IndexedDB)。 | `client-api.detailSpeed` 引入 3000ms 硬超时截断与 Promise.allSettled 并发测速防阻塞；EWMA 断路器动态评级；非侵入式极速源浮动胶囊提示。 | **(1) 蓝光多音轨与多分辨率（画质）无法自由选择**；**(2) 百集以上选集未引入虚拟化滚动**，仅靠 50 集分组折叠，上千集长漫仍存在滚动开销；**(3) 外挂字幕音画时间轴不可微调**。 |

| **观看历史** (`/history`) | 本地 Dexie IndexedDB 存储（最大 50 条）、观看百分比进度条、标题实时过滤、单条删除（含 5 秒撤销）、一键清空、点击秒级断点续播。 | 修复了历史面板封面挤压与排版坍塌问题。 | 历史数据纯本地存储，换设备或换浏览器即变为数据孤岛，缺乏轻量级多设备同步或导出恢复增强。 |
| **设置中心** (`/settings`) | 点播源 CRUD 与勾选、数据源订阅（JSON/TVBox）静默同步、播放与过滤偏好、图片代理模式切换、配置 JSON 导入导出。 | 增加源健康度记录与失败统计。 | 缺乏针对所有点播源的一键“批量并行健康度测速与按延迟自动加权排序”工具，用户需手动管理几十个源。 |

## 2. 竞品深度对标与关键体验痛点分析

团队深入对标业内标杆流媒体聚合与播放应用（如 **Vidhub**、**Infuse**、**Emby / Jellyfin** 及 **Netflix**），结合真实观影场景，提炼出 LibreTV 当前最迫切的 4 大体验断层：

```
┌────────────────────────────────────────────────────────────────────────┐
│                        用户观影全流程关键体验痛点                         │
├────────────────────────────────────────────────────────────────────────┤
│ 1. 视听控制痛点   │ 蓝光原盘/动漫多国音轨无法切换；HLS 清晰度无法强制锁定1080P/4K │
│ 2. 长剧滚动卡顿   │ 千集大剧（如《柯南》《海贼王》）分段折叠体验割裂，缺少虚拟滚动  │
│ 3. 追剧提醒弱感知 │ 收藏了影视但新集更新无法在首页第一眼感知，仍需手动进播放页看    │
│ 4. 影视探索断层   │ 播放页看到喜欢的演员/导演，无法点击进入其专属影视作品集         │
└────────────────────────────────────────────────────────────────────────┘
```

1. **痛点一：蓝光/原盘高清源的音轨与画质不可控（对标 Vidhub / Infuse）**
   - **现状**：海外蓝光无删减源与优质切片源往往内嵌“国英双语”、“粤语原声”等多音轨，且自适应提供 720P/1080P/4K 多码率切片。但当前系统默认由播放器自动选择，用户经常遇到“默认播英语配音想听国配却无处切换”，或“网络抖动时画质骤降至 360P 却无法手动锁定 1080P”的窘境。
   - **诉求**：提供可视化的多音轨选择菜单与 HLS 视频清晰度档位切换菜单。

2. **痛点二：千集长剧选集滚动的性能与交互割裂（对标 Emby / 腾讯视频）**
   - **现状**：目前系统采用“每 50 集一组”的硬分段胶囊按钮。遇到 1000+ 集的长剧时，胶囊栏长达 20 多个，用户在各组之间切换查找极其繁琐；且当前分组内直接挂载所有 DOM 节点，若快速切换易引发渲染微卡顿。
   - **诉求**：引入 `@tanstack/react-virtual` 虚拟化滚动视口，实现连续平滑滚动（Virtual Scrolling），同时保留区间快跳锚点，DOM 节点数恒定在 50 个以内，帧率稳定在 60fps。

3. **痛点三：追剧更新被动滞后，缺乏首页聚合动态（对标 苹果 TV app / B站）**
   - **现状**：用户在播放页点击了“加入追剧单”，目前仅在播放页内对比集数更新。用户打开首页无法快速发现“我追的哪几部剧更新了第几集”，导致追剧粘性不足。
   - **诉求**：在首页顶部核心位置设立“我的追剧·最近更新”动态专区，实时展示有最新集数的剧集卡片并标亮“更新至 XX 集”，点击直达最新集播放。

4. **痛点四：演职员与内容探索图谱断层（对标 TMDB / 豆瓣 / 奈飞）**
   - **现状**：播放页虽然拉取并展示了导演、主要演员列表，但这些名字均为静态文本。系统后端实际上已经集成了 `/api/media/person` 接口，但前端未打通点击交互。
   - **诉求**：点击演职员姓名，弹出人物卡片或作品专区，一键探索该演员/导演的全网影视代表作。

## 4. 重点需求详细定义与量化验收标准 (AC)

### 4.1 【P0 核心必做】REQ-P0-01：HLS 视频多清晰度与内置多音轨自由切换

- **功能定义**：在播放器控制栏与设置面板中，自动侦测当前 HLS 视频流内嵌的所有视频码率档位（Levels，如 4K 2160P、1080P 高清、720P 标清）以及内置的多语言音频轨道（Audio Tracks，如 国语、英语、粤语、日语原声），并提供友好直观的切换菜单。
- **用户故事**：
  > 作为一名追番或观赏蓝光电影的观众（R1），  
  > 我想要在播放器中自由切换音轨（如从英语切换至原声日语）并手动锁定 1080P/4K 画质，  
  > 以便享受最原汁原味的高保真视听体验，避免弱网下系统自动降级到马赛克画质。
- **业务价值**：极大提升蓝光资源与动漫作品的观看品质，达到对标主流专业播放器的专业度。
- **技术可行性分析**：
  - 基于当前播放器使用的 `hls.js` 实例：
    - `hls.levels` 可获取全部码率档位，`hls.currentLevel = levelIndex`（或 `-1` 自动）可直接无缝热切换画质；
    - `hls.audioTracks` 可读取内嵌音轨列表，`hls.audioTrack = trackId` 可在播放进行中毫秒级切换音轨；
  - 封装进 `useHlsPipeline.ts`，并通过 `ArtPlayer` 的 `controls` 或 `setting` API 添加“画质”、“音轨”子菜单，无需任何后端变更。
- **量化验收标准 (Acceptance Criteria)**：
  - **AC-P0-01.1**：*Given* 播放支持多码率切换的 HLS 切片流；*When* 点击控制栏“画质”选项；*Then* 列表清晰显示“自动 (Auto)”、“1080P”、“720P”等所有可用规格，并高亮当前档位；
  - **AC-P0-01.2**：*Given* 用户选择某一固定画质（如 1080P）；*When* 切换档位后；*Then* 视频在 ≤ 1.5 秒内继续播放，不重置播放进度（时间戳跳变 < 1 秒），播放器不再自动受网络抖动影响降级；
  - **AC-P0-01.3**：*Given* 视频内嵌多条音频轨道（如国语/原声）；*When* 用户切换音频轨道；*Then* 音轨在 ≤ 800ms 内平滑切换至新音轨，音画保持严格同步；
  - **AC-P0-01.4**：*Given* 视频仅包含单一画质或单一音轨；*When* 渲染播放器控制菜单；*Then* 对应项友好显示“默认”或自适应隐藏，不展示破损或不可点击的占位菜单。

### 4.2 【P0 核心必做】REQ-P0-02：长剧选集 `@tanstack/react-virtual` 虚拟化滚动重构

- **功能定义**：对播放页侧栏（`WatchSidebar`）的剧集选集容器进行彻底的虚拟滚动（Virtual Scrolling）改造，无论剧集总数为 50 集还是 1200 集，均采用视口动态挂载渲染机制，彻底消除超长剧集选集时的 DOM 节点爆炸与内存泄漏。
- **用户故事**：
  > 作为一名追看《柯南》《航海王》等长篇动漫或百集连续剧的追剧用户（R2），  
  > 我想要在剧集列表中顺滑滚动浏览与快速跳转任意集数，  
  > 以便在数千集中秒速定位到目标集数，且页面无任何掉帧与顿挫感。
- **业务价值**：根治长剧场景下的前端性能衰减隐患，将选集操作性能提升至顶尖水准。
- **技术可行性分析**：
  - 项目根目录 `package.json` 中已预装官方成熟依赖 `@tanstack/react-virtual`（v3.13.0）；
  - `WatchSidebar.tsx` 当前采用的是硬性分页折叠（每 50 集切一组）。重构方案：在侧栏保留“百集快速区间锚点条”（快速跳转到目标区间），但在选集主展示区使用 `useVirtualizer` 挂载网格或列表，可视区外 DOM 自动回收，真实 DOM 节点稳定保持在 40~60 个以内。
- **量化验收标准 (Acceptance Criteria)**：
  - **AC-P0-02.1**：*Given* 加载一部集数 ≥ 1000 集的影视作品；*When* 用户在选集列表内进行高速往返滚动；*Then* 滚动帧率全程稳定在 ≥ 58fps（Chrome Performance 面板监控），无明显掉帧；
  - **AC-P0-02.2**：*Given* 选集列表在任何滚动位置；*When* 审查 DOM 结构；*Then* 选集渲染容器内的真实 DOM 节点数严格控制在 ≤ 60 个，不随总集数线性膨胀；
  - **AC-P0-02.3**：*Given* 用户点击顶部百集区间锚点（如“501-600”）；*When* 触发快跳；*Then* 虚拟列表瞬间平滑滚动至第 501 集可视位置，且当前播放集始终保持醒目高亮与焦点样式；
  - **AC-P0-02.4**：*Given* 正序/倒序切换按钮被触发；*Then* 虚拟列表能够即时逆转索引序列，并重新对齐当前播放集的位置。

### 4.3 【P0 核心必做】REQ-P0-03：首页“我的追剧·最近更新”动态流专区与智能红点

- **功能定义**：在首页顶部（Hero 轮播下方、推荐流上方）新增专属的“我的追剧·更新动态”横滑楼层。自动比对用户本地追剧单中的影视作品与采集源/元数据库的最新集数。若发现已更新新集，则置顶展示并标明更新角标（如“更至 24 集 / 上次看至 20 集”），点击即刻直达最新集播放。
- **用户故事**：
  > 作为一名同时追看多部热播剧与新番的用户（R2），  
  > 我想要一打开 LibreTV 首页就能看到哪些剧今天更新了新集数，  
  > 以便一键续播最新集，不再需要一部部去翻看各剧的更新情况。
- **业务价值**：将首页从单纯的“内容发现”升级为“追剧工作台”，成倍提高次日回访率与观影粘性。
- **技术可行性分析**：
  - 数据源已在 Dexie `db.favorites` 中完整保存了 `lastKnownEpisodes`（上次已知集数）、`seenEpisodes`（已看集数）与 `remarks`；
  - 首页现已有 `remarksQuery` 与 `syncRecentUpdates`（主力源集数静默同步机制），只需将 `db.favorites` 与该数据建立高效对比，筛选出 `latestEpisode > max(seenEpisodes)` 的条目，渲染为沉浸式横滑卡片行。
- **量化验收标准 (Acceptance Criteria)**：
  - **AC-P0-03.1**：*Given* 用户追剧单中有且仅当影视作品出现新集数（或备注发生变化）；*When* 打开首页；*Then* 首页顶部立即呈现“追剧更新”专属楼层，展示带有金色发光“NEW”或“已更新”角标的海报卡片；
  - **AC-P0-03.2**：*Given* 更新卡片展示；*Then* 卡片底部清晰标注文案：如“已看第 12 集 · 更新至第 15 集”；
  - **AC-P0-03.3**：*Given* 用户点击该更新卡片；*Then* 自动跳转进入播放页并直接载入最新的一集（第 13 集或第 15 集），不需要用户再次手动点击选集；
  - **AC-P0-03.4**：*Given* 用户追剧单为空或全部剧集已追平最新集；*Then* 首页自动优雅折叠该专属专区，不留任何空白占位，确保首页视觉紧凑。

### 4.4 【P0 核心必做】REQ-P0-04：播放线路 QoS 综合监控面板重构与“一键秒切极速源”

- **功能定义**：对播放页的线路测速体验进行全方位打磨。将分散的“测速换源弹窗”与播放器下方简略的“播放线路横滑栏”深度融合为一体化、高信噪比的“多源 QoS 线路雷达监控抽屉”。以实时 Ping 延迟、QoS 健康评级徽章、集数完整度及断路器状态进行全局动态排序，并提供强烈的“一键秒切最快线路”快捷操作。
- **用户故事**：
  > 作为一名对播放流畅度敏感的用户（R1），  
  > 我想要清晰透明地看到所有线路的当前网速排位，并在当前线路卡顿时一键换到最快线路，  
  > 以便感知多源选优带来的技术红利，彻底告别卡顿与手动排查慢源的痛苦。
- **业务价值**：将 JIT 多源并发测速的核心技术壁垒外化为用户极致可感知的爽点。
- **技术可行性分析**：
  - 核心逻辑已在 `use-watch-engine.ts` 与 `source-circuit-breaker.ts` 中实现（EWMA 平滑延迟计算、QoS 评级、Promise.allSettled 3000ms 超时截断）；
  - 目前已有 `SwitchSourceModal`，但其以居中弹窗展示，且测速需重复触发。重构为右侧滑出或底部半屏抽屉（Drawer），并将实时测速结果回写全局 Store，使当前播放源与候选源延迟实时对比，支持“一键直切最快源”。
- **量化验收标准 (Acceptance Criteria)**：
  - **AC-P0-04.1**：*Given* 打开测速线路面板；*When* 并发测速执行中；*Then* 线路列表按响应延迟从快到慢升序实时动态重排，单源超时严格限制在 ≤ 3000ms；
  - **AC-P0-04.2**：*Given* 测速完毕后；*Then* 每条线路卡片完整展示：源名称、实时延迟（如 `86ms`）、QoS 等级徽章（绿/琥珀/红）、集数覆盖情况（如 `40集全`）及断路器状态（健康/受阻）；
  - **AC-P0-04.3**：*Given* 检测到存在比当前线路快 30% 以上的极速线路；*When* 面板顶端呈现“一键切换至最快线路 [源名 · XXms]”按钮；*Then* 用户点击后，在 ≤ 1.5 秒内完成换源播放，且播放进度误差 ≤ 1 秒；
  - **AC-P0-04.4**：*Given* 播放过程中当前线路突发网络异常；*Then* 抽屉指示灯变为警告色，并在触发自动故障转移时，面板同步高亮新启用的线路并弹出清晰的状态迁移 Toast。

## 5. 推荐版本范围与取舍理由 (PM Recommendation)

作为产品经理，在平衡**研发资源、交付风险、架构稳定性与用户感知价值**后，给出以下本次迭代范围推荐建议：

```
┌────────────────────────────────────────────────────────────────────────┐
│                   本次迭代推荐纳入范围 (Recommended Scope)                  │
├────────────────────────────────────────────────────────────────────────┤
│ ✅ 4 个 P0 核心项：                                                     │
│   1. REQ-P0-01: HLS 视频多清晰度与内置多音轨自由切换 (视听基准)          │
│   2. REQ-P0-02: 长剧选集 @tanstack/react-virtual 虚拟滚动重构 (性能基建)│
│   3. REQ-P0-03: 首页“我的追剧·最近更新”动态流专区与智能红点 (留存驱动)    │
│   4. REQ-P0-04: 播放线路 QoS 综合监控面板重构与一键秒切极速源 (核心壁垒) │
│                                                                        │
│ 🌟 2 个高性价比 P1 项 (建议纳入)：                                      │
│   5. REQ-P1-01: 外挂字幕时间轴微调与步进校准 (解决字幕痛点，成本极低)     │
│   6. REQ-P1-02: 演职员档案全网代表作穿透探索 (盘活后端现有 API，体验惊艳) │
├────────────────────────────────────────────────────────────────────────┤
│ ⏸️ 建议暂缓/顺延至下阶段项 (Deferred Scope)：                          │
│   - REQ-P1-03: 点播源全量批量测速与重排 (已有单源测速，批量测速对网速开销大)│
│   - REQ-P1-04: WebDAV/Gist 云同步 (涉及网络鉴权与冲突合并，适合专项推进)  │
│   - REQ-P2-01 / P2-02: 画中画与 EPG 节目单优化 (非阻断性边缘体验)        │
└────────────────────────────────────────────────────────────────────────┘
```

### 取舍理由深入阐述：

1. **为什么必须做 4 个 P0？**
   - **画质/音轨切换** 是流媒体播放器之所以被称为“专业播放器”的及格线。尤其在当前已有海外蓝光专线的背景下，没有音轨切换等于废掉了双语音频的价值。
   - **长剧选集虚拟滚动** 是避免前端崩溃的技术硬通货，依赖库已在项目中引入，开发周期可控，必须在长剧用户产生抱怨前彻底铲平。
   - **追剧动态专区** 是提升用户黏度的最直接手段，从“每次都要搜索想看什么”转变为“打开直接看今天更新了什么”。
   - **QoS 线路雷达监控** 将后台复杂的并发测速能力转化为前台可见的确定性感官信任，是 LibreTV 与传统普通采集站的最本质区别。

2. **为什么推荐带入 REQ-P1-01（字幕微调）与 REQ-P1-02（演职员穿透）？**
   - **字幕微调** 仅需在现有字幕状态机增加一个偏移变量计算，代码量小（约 50 行），但能解决观影中“字幕早半秒剧透”的致命体验问题。
   - **演职员穿透** 系统后端早在先前版本就开发完毕了 `/api/media/person` 接口，前端只需完成卡片交互与触发，投产比（ROI）极高。

3. **为什么建议暂缓 WebDAV 云同步 (REQ-P1-04)？**
   - 跨设备云同步涉及多端冲突合并算法（CRDT 或时间戳策略）、第三方网盘授权与敏感凭据保护。将其放入本版本会显著拉长测试与交付周期。当前已有 JSON 导入导出与 QR 扫码秒级接力，足以应对日常应急迁移。

## 6. 技术架构影响与实现可行性

本次推荐迭代严格遵循**“无需引入外部服务、零破坏性架构侵入、纯前端与既有轻量 API 协同”**的工程原则：

```
┌────────────────────────────────────────────────────────────────────────┐
│                        前端组件与状态流转改造拓扑图                         │
└────────────────────────────────────────────────────────────────────────┘
                                    │
    ┌───────────────────────────────┼───────────────────────────────┐
    ▼                               ▼                               ▼
【首页更新流】                  【播放器核心】                  【选集与交互】
HomePage (/)                   PlayerShell                     WatchSidebar
  │                              │                               │
  ├─► db.favorites 追剧单比对      ├─► hls.audioTracks 多音轨切换   ├─► useVirtualizer
  ├─► syncRecentUpdates 增量侦测   ├─► hls.levels 画质自选锁定      │   虚拟滚动网格渲染
  └─► ContinueWatchingRow 渲染    ├─► SubtitleLayer 毫秒步进偏移    └─► 百集快跳区间联动
                                 └─► useWatchEngine QoS 雷达抽屉
```

1. **无破坏性重构**：所有状态变更均在客户端本地（Dexie IndexedDB、Zustand、hls.js）完成，不变更数据库表结构，向下完全兼容已有本地历史与收藏数据。
2. **零新增服务端开销**：充分利用已有接口（`/api/media/person`、`/api/detail`、`/api/search`），不给服务端造成额外计算负担。
3. **质量防线**：新增测试覆盖音轨切换回调、虚拟化渲染范围计算、追剧单集数差量比对算法，确保 100% 保持当前 368+ 测试项的绿色通过率。
